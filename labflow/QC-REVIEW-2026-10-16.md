## 2. Findings (severity, file:line, evidence)

### F1 — MEDIUM (top must-fix). Any transient Windows lock on a save → HTTP 500 (non-JSON), lost concurrent writes, duplicate notifications
`patients.py:180-206` (`save`/`os.replace`), `patients.py:215-236` (`update_step` read-modify-write), `app.py:126-143` (`_retry_windows_lock`), `app.py:287` (only call site), `engine.py:166-168, 201-205, 223, 254-262` (all other saves).

- The retry helper exists but wraps **only** the `start_patient` save inside `POST /api/patients`. All other mutations (`begin`/`complete`/`skip`/`redo`/`measurement`/`link`, and the initial draft save inside `store.create`) call `store.save` unguarded.
- Repro (deterministic): inject one `PermissionError` into `save()` → every mutation endpoint returned **`500 Internal Server Error`** (plain text — not the documented `{"ok": false, ...}` JSON; `app.py:26`), including `create` on its *first* (draft) save; `create` on its *second* (start_patient) save succeeded (200) thanks to the retry.
- Repro (realistic race): 16 threads calling `update_step` on one patient (5/5 trials): **11–14 of 16 saves raised `PermissionError [WinError 5]`**, and the final file retained **1/16** of the distinct fields. Two threads calling `complete_step` concurrently fired **2 `step_completed` notifications** for one station (`probe_engine_store.py` [16]).
- Why it is reachable: FastAPI runs these sync endpoints in a threadpool and the UI does not disable buttons while a request is in flight (`static/labflow.js:265-285`), so a fast double-click on “Done/Skip” sends two concurrent POSTs to the same patient file; Windows `os.replace` then fails on one of them. Also the guard in `_require_current` (`app.py:236-247`) is checked against a patient snapshot loaded at request start while the engine re-reads inside `complete_step` — under an unlucky interleave the second click can complete a *later* station with the first click’s form data (narrow TOCTOU window; not observed, inferred from `engine.py:182-206`).
- Impact: confusing 500 toast (`static/labflow.js:45-51` shows `HTTP 500`), a lost/overwritten write, and duplicate Telegram “DONE” messages. No file corruption (tmp+`os.replace` is atomic; failing saves clean up their tmp file — verified).
- Fix direction (no edits made): wrap all mutation endpoints in the existing retry helper (or add a tiny per-patient lock), and map `OSError` to a JSON error response; optionally disable buttons client-side in-flight.

### F2 — LOW. Duplicate notifications are possible (double begin, redo→re-complete)
`engine.py:158-173` (`begin_step` not guarded against re-begin), `engine.py:203-208` (second `flow_completed` after a redo), `engine.py:238-264` (redo reopens a completed patient).

- Evidence: two `begin_step` calls fired `step_started` twice for the same station; skip-all → redo `intake` → complete again produced a **second `flow_completed`** (Telegram “Flow DONE” twice), by design of “redo reopens a completed flow” but with no de-dup or “reopened” marker in the message. Concurrent double-`complete` also fires `step_completed` twice (F1 evidence).
- Recommendation: either accept+document, or suppress repeat `flow_completed` until the flow was genuinely reopened/closed anew (e.g. only notify `flow_completed` on a transition), and make `begin_step` idempotent for an `in_progress` station.

### F3 — LOW. Unbounded patient name → 500 (or 400) on create; no length cap anywhere
`app.py:272-288` (no length check), `patients.py:116-122` (`_new_id`), `patients.py:191-193` (`tempfile.mkstemp`), `static/index.html:32` (no `maxlength`).

- Evidence: name of 190–217+ chars (boundary ≈ `239 − len(patients_dir)` chars; ~171 on the shipped data path, driven by the 260-char total-path limit) → **`FileNotFoundError` in `tempfile.mkstemp` → 500 “Internal Server Error”**; 100 000 chars → `ValueError: open: path too long for Windows` → 400 `{"ok": false, "error": ...}`. Nothing partial is left behind.
- Why it matters: pasting a long line of text into the Name field (a plausible user action; no `maxlength`, no trim-to-N) yields a 500. Fix: cap `name` length (e.g. 120 chars) at the API and add `maxlength` in the form.

### F4 — LOW. Malformed/non-object JSON bodies return 422 without the `ok` envelope
`app.py:26` (“every response is JSON with an `ok` boolean”) vs unhandled Starlette `RequestValidationError`.

- Evidence: body `{"name": "X",` → `422 {"detail":[{"type":"json_invalid",...}]}`; JSON array body → 422 `detail`; `text/plain` body → 422. Requests are safely rejected; only the response envelope contract is broken (client shows `HTTP 422`, `labflow.js:47`).

### F5 — LOW. `/link` accepts any app name and completes whatever station is current (no app↔station affinity)
`app.py:352-381`; UI “Link latest” button offered for every available app (`static/labflow.js:422-429`).

- Evidence: `{"app": "evilapp", "session_id": 12345}` → 200, stored under `linked_sessions.evilapp`, and `step_completed: true` (the current step was closed). Sending a RunTrack session while at the Bertec station would close the Bertec station with a foreign link. The station id *is* recorded in the step result (`app.py:370-371`), so data is attributable, but the UI/MVP invites a mismatch.
- Recommendation: validate `app` against the current station’s `app`/`capture.probe` (or drop `step_completed` for mismatches).

### F6 — LOW. Corrupt patient JSON vanishes silently (no log, no quarantine); `count()` disagrees with `list()`
`patients.py:155-165` (`get` → `None` on OSError/JSONDecodeError/non-dict), `patients.py:167-178` (`list` skips), `patients.py:111-113` (`count` still counts the file).

- Evidence: corrupted file → `get` → `None`, patient absent from `list()` and the UI (404 “unknown patient”), file left in place, **nothing logged**. With 1 valid + 2 corrupt files: `count() == 3`, `len(list()) == 1`. `count()` is currently unused by the app (dead helper) but is a trap for future callers.
- Recommendation (nice-to-have): log/quarantine unreadable files (`<id>.json.bad`) so a corrupted record is visible instead of “gone”.

### F7 — LOW. Non-string `data_dir` in `config.json` crashes the app at boot with a raw `TypeError`
`app.py:82-90` (`load_config` validates only top-level dict), `app.py:93-102` (`default_data_dir`), `app.py:150`.

- Evidence: `default_data_dir({"data_dir": 17})` raises `TypeError: argument should be a str or an os.PathLike …`; since this runs at module import, a config typo prevents the server from starting at all (no friendly message). Same class: junk `port` only affects `python -m labflow.app` (`app.py:416-424`; the shipped `.cmd` hardcodes `--port 8790`).

### F8 — INFO. Looseness that is tolerable but worth knowing
- `update_step` accepts **arbitrary field keys** despite the “Allowed keys” docstring (`patients.py:218-236`); unbounded step dicts can be written (only internal callers today).
- Engine treats a non-list `results` value in a hand-edited patient file as an iterable: `results="abc"` → merged as `['a','b','c']` (`engine.py:189-191`, evidence [7]).
- `load_workflow` silently falls back to `DEFAULT_WORKFLOW` when `workflow.yaml` raises `ValueError` (`app.py:105-114`) — a typo’d station file silently swaps the flow with no log; currently harmless because `workflow.yaml` ≡ `DEFAULT_WORKFLOW` (field-level diff: NONE, verified).
- `/probes` propagates an exception if the injected `probe_fn` raises → raw 500 (`app.py:386-393`); unreachable with the shipped `probe_all`, which never raises (`result_probes.py:285-299`).

### F9 — INFO (security posture). Loopback-only, no auth, no Host/Origin validation
- Binding is `127.0.0.1` only — verified by `netstat` for `:8790`, plus `.cmd`/docs (`Start LabFlow.cmd`, `app.py:10`). No CORS middleware, no `Host` validation (`Host: evil.example.com` accepted, 200), `/docs` and `/openapi.json` exposed on loopback.
- Consequence: a hostile page in the operator’s browser could still try DNS-rebinding-class requests to the loopback API (cross-origin `application/json` fetches are preflighted and blocked by the missing CORS headers, and `text/plain` bodies are rejected 422 — both verified). Accepted risk for a local tool; `TrustedHost` middleware would be cheap hardening. Not exploited, reasoned + probed only.

### F10 — NITS (cosmetic)
- `static/labflow.js:154-157` reads `progress.percent`, but the API sends `pct` (`engine.py:296-303`) → the fallback `Math.round(done/total*100)` always runs (same value; dead branch).
- Numeric coercion of capture fields (`labflow.js:307-321`, `369-371`) never triggers for the shipped `workflow.yaml` because `capture.fields` are plain strings (no `type`), so typed values are stored as strings. Harmless today.
- Token-file edge: `TELEGRAM_BOT_TOKEN=abc # prod` yields the token *including* ` # prod` (`notify.py:53-55,337-353`) → the Telegram send fails 404, is logged, returns `False` (never raises). Multi-token file: first match wins (deterministic).

## 3. Top must-fix

1. **F1 — make every mutating endpoint resilient to Windows file-lock races and return JSON errors.** Reuse `_retry_windows_lock` (or a per-patient lock) for `begin/complete/skip/redo/measurement/link` and the draft save in `create`, and map `OSError` to an `ok:false` response. This is the only issue with a realistic ordinary-use trigger (double-click) and a real consequence (500 toast + lost/overwritten write + duplicate alerts).
2. **F3 — cap patient-name length** (API + `maxlength` in the form) so pasting long text can’t produce a 500.

Everything else is LOW/INFO: recommended clean-ups, not blockers.
